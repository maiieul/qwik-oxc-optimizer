**is_const.rs -- Implement `is_const_expression()`:**
Determine whether a JSX prop value expression is a compile-time constant (goes in const props) vs a runtime variable (goes in var props). This is critical for correct prop classification.

Return `true` for:
- String literals, numeric literals, boolean literals, null literals, bigint literals, regex literals
- Template literals with NO expressions (`\`text\``)
- Template literals with only const sub-expressions
- `typeof` expressions on any operand (typeof is always a string)
- Ternary expressions where both branches and the test are all const
- Binary expressions where both sides are const (arithmetic, comparisons)
- Unary expressions on const operands (`!true`, `-1`)
- Object expressions where ALL property values are const
- Array expressions where ALL elements are const
- Parenthesized expressions wrapping a const expression

Return `false` for:
- Identifier references (variables are never statically const for prop classification purposes -- BUT there are nuances: imported CSS modules like `styles.foo` are const. For now, identifiers are var.)
- Member expressions (signal.value, store.prop, etc.)
- Call expressions (function calls are never const)
- Any expression containing a function call
- Arrow/function expressions (these are closures, not const values)

**IMPORTANT nuance from specs:** The const/var classification for JSX props is NOT purely about whether the value is statically known. It's about whether the value can change reactively. Study the spec outputs:
- `styles.foo` (imported CSS module) -> **const prop** (imported values don't change)
- `signal` (signal object) -> **const prop** (the signal OBJECT is const; .value is reactive)
- `signal.value` -> needs `_wrapProp` wrapping (reactive access)
- `dep` (imported identifier) -> **const prop** (imported values are const)
- `dep.thing` -> **const prop** (member access on imported is const)
- `globalThing` -> **var prop** (unresolvable identifier is var)
- `window.document` -> **var prop** (global member access is var)
- `count % 2 === 0` (where count is derived from props) -> **var prop**

The actual classification depends on whether the identifier is imported, a signal, a store, etc. For now, implement a simpler version:
- Literals, template literals without expressions -> const
- Everything else -> var
This will be refined in later phases if needed. The signal wrapping logic (below) handles the reactive cases independently of const/var classification.

**Signal wrapping logic -- integrate into JSX prop classification from Plan 11-01:**

During JSX prop iteration (in the exit_jsx_element handler from 11-01), for each attribute value expression, apply signal wrapping BEFORE deciding const vs var:

1. **`_wrapProp(signal)` -- Form 1 (signal.value access):**
   Pattern: `expr.value` where `expr` is an identifier that was declared via `useSignal()` or is a prop parameter.
   Detection: The expression is a `MemberExpression` with property name `.value` and the object is an identifier.
   BUT: Only wrap if the object is NOT a function call result. `signal.value()` should NOT be wrapped (it's a method call, not reactive access). Specifically, only wrap `X.value` where X is a simple identifier, NOT a call expression result.
   Transform: Replace `signal.value` with `_wrapProp(signal)`.

   More precisely from specs: `_wrapProp` is used when the prop value is `signal.value` (MemberExpression with .value property). The signal object itself (`signal` without `.value`) is passed as a const prop directly.

2. **`_wrapProp(source, "propName")` -- Form 2 (store/props property access):**
   Pattern: `source.propName` where `source` is a `_rawProps` parameter or a store.
   Detection: MemberExpression where object is _rawProps and `.value` is NOT the property.
   Transform: `_rawProps.fromProps` becomes `_wrapProp(_rawProps, "fromProps")`.
   This form is used when the prop access is on a reactive source but the property name is not `.value`.

3. **Non-wrapping rules (from specs):**
   - `signal.value()` -- function call on .value -> do NOT wrap (it's a method call)
   - `mutable(signal)` -- function call result -> do NOT wrap
   - `signal` (without .value) -> const prop directly, no wrapping

**_fnSignal wrapping for computed expressions:**

Pattern: Any expression in a JSX prop that contains reactive sub-expressions (signal.value, store.prop, _rawProps.prop) mixed with other operations, where ALL non-const sub-expressions are reactive sources.
Examples: `signal.value + 1`, `store.active ? 'yes' : 'no'`, `{props: fromProps}`.
Detection: The expression contains at least one reactive source AND is not a simple `.value` access (which would be _wrapProp from Task 1 instead).

Transform:
a. Create a hoisted arrow function `_hfN` that takes the reactive sources as parameters (p0, p1, ...) and returns the computed expression with sources replaced by parameter references.
b. Create a hoisted string constant `_hfN_str` containing the minified string representation of the function body.
c. Replace the original expression with `_fnSignal(_hfN, [source1, source2, ...], _hfN_str)`.

**Hoisted function construction:**
- Number the functions sequentially per module/segment: `_hf0`, `_hf1`, `_hf2`, ...
- The arrow function parameters are named `p0`, `p1`, ... corresponding to each unique reactive dependency.
- In the function body, replace each reactive source with its parameter name.
- The string representation `_hfN_str` should be a minified version of the function body. Use `oxc::codegen::Codegen` to serialize the body expression, then extract just the body text (strip the `(p0) =>` prefix from the serialized arrow).

**Reactive source detection (what counts as a dependency for _fnSignal):**
- `signal` (identifier declared via useSignal) -> dep
- `store` (identifier declared via useStore) -> dep
- `_rawProps` -> dep
- `row` (identifier from .map() callback parameter accessing `.value`) -> dep
- Imported identifiers (`dep`, `styles`) -> NOT a dep (imports are const)
- Global identifiers (`window`, `globalThing`) -> NOT a dep (globals are var but not tracked reactively)

For now, use a simplified heuristic: if the expression contains any MemberExpression with `.value` property, or any reference to `_rawProps`, treat it as needing `_fnSignal`. The deps array contains the root objects of those member expressions.

**Non-wrapping rules for computed expressions (from specs):**
- `signal.value + unknown()` -- has unknown function call -> do NOT wrap (can't track deps)
- `signal.value + dep` -- mixed signal + import -> do NOT wrap with _fnSignal (put in var props as-is). In example_derived_signals_div, `noInline4: signal.value + dep` goes in **var props** as-is (no wrapping). So: if expression has both reactive sources AND non-reactive non-const parts (like imported identifiers used as values), it goes to var props without wrapping.

Revised rule: Only use `_fnSignal` when ALL non-const sub-expressions in the expression are reactive sources (signals, stores, _rawProps). If there are non-reactive non-const sub-expressions (like globals, unknown identifiers), put the whole expression in var props without wrapping.

**ImportTracker additions:**
- `needs_fn_signal: bool` -- import `_fnSignal` from `@qwik.dev/core`

**Hoisted function storage:**
Add a field to QwikTransform: `hoisted_functions: Vec<(String, Expression, String)>` where each entry is `(name, arrow_expr, string_repr)`. In `exit_program`, prepend these as `const _hfN = (p0) => ...;` and `const _hfN_str = "...";` declarations before the existing program body.

For segment strategy, hoisted functions for expressions inside segment bodies should be placed at the top of the segment module code, not the main module. This is handled by building the hoisted declarations as string code in the segment's code_move step. Alternatively, track which hoisted functions belong to which segment and include them in the segment code construction. The simpler approach: since hoisted functions are created during JSX prop processing which happens during traverse (before segment code extraction), and the segment body code is serialized after traverse, the hoisted functions will appear in the serialized segment code if they reference segment-local identifiers. BUT: per the spec outputs, hoisted functions appear BEFORE the segment export. So they need to be prepended during code_move.

**Approach:** During traverse, when a JSX prop needs _fnSignal wrapping:
1. Build the hoisted arrow function body with p0/p1 params.
2. Serialize the body to get `_hfN_str`.
3. Store the hoisted function info.
4. Replace the prop value with `_fnSignal(_hfN, [deps], _hfN_str)`.

The hoisted function declarations are inserted at the top of the containing scope (module or segment) during exit_program / code_move.

**Input binding transformation (CONV-12):**

During JSX prop iteration (in exit_jsx_element), detect `bind:value` and `bind:checked` attributes:

1. **`bind:value={signal}`:**
   Replace with TWO const props:
   - `"value": signal` (the signal object as a const prop)
   - `"q-e:input": inlinedQrl(_val, "_val", [signal])` (event handler QRL)

   This requires:
   - Import `_val` from `@qwik.dev/core`
   - The `inlinedQrl` call wraps the `_val` identifier (not an arrow function -- just the imported identifier reference)
   - The captures array contains `[signal]` (the bound signal)

   Replace with TWO const props:
   - `"checked": signal` (the signal object as a const prop)
   - `"q-e:input": inlinedQrl(_chk, "_chk", [signal])` (event handler QRL)

   This requires:
   - Import `_chk` from `@qwik.dev/core`

3. **`bind:other={signal}` (any other bind: attribute):**
   Pass through as-is in const props: `"bind:other": signal`
   No transformation.

4. **Merging with existing event handlers:**

The spec output shows they merge into an array: `"q-e:input": [inlinedQrl(_val, "_val", [signal]), qrl(i_hash, "name")]`.
