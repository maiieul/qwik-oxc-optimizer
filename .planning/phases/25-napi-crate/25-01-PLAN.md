**4. Create `crates/qwik-napi-oxc/src/lib.rs`:**

This is the core of the NAPI binding. It must:

a) Define `NapiTransformModulesOptions` -- a NAPI-specific input struct that matches the JS wire format from `convertOptions()` in optimizer.ts. Key differences from the internal OXC types:
   - `entry_strategy` is a plain string (`"smart"`, `"segment"`, etc.), NOT a tagged enum
   - `manual_chunks` is a separate `Option<HashMap<String, String>>` field (from `opts.entryStrategy?.manual`)
   - All other fields match the internal OXC `TransformModulesOptions` (camelCase via serde)

b) Define a conversion function `from_napi_options(napi_opts: NapiTransformModulesOptions) -> qwik_optimizer_oxc::TransformModulesOptions` that:
   - Converts `entry_strategy: String` to the internal `EntryStrategy` enum (match on "inline" | "hoist" | "single" | "hook" | "segment" | "component" | "smart", default to Segment)
   - Drops `manual_chunks` (the OXC optimizer doesn't use manual chunks in its entry strategy logic -- verified: OXC EntryStrategy enum has no manual field, and SWC's Rust side also ignores manualChunks)
   - Passes through all other fields directly

c) Export `transform_modules` as a NAPI function:
   ```rust
   #[napi]
   pub fn transform_modules(opts: serde_json::Value) -> napi::Result<serde_json::Value> {
       // Deserialize from JS wire format
       let napi_opts: NapiTransformModulesOptions = serde_json::from_value(opts)
           .map_err(|e| napi::Error::from_reason(format!("Invalid options: {e}")))?;
       // Convert to internal format
       let internal_opts = from_napi_options(napi_opts);
       // Call the optimizer
       let output = qwik_optimizer_oxc::transform_modules(internal_opts)
           .map_err(|e| napi::Error::from_reason(format!("Transform error: {e}")))?;
       // Serialize to JS wire format
       serde_json::to_value(&output)
           .map_err(|e| napi::Error::from_reason(format!("Serialization error: {e}")))
   }
   ```

   NOTE: Use `serde_json::Value` as the NAPI boundary type (not a typed struct) because napi-rs's serde-json feature handles `JsObject <-> serde_json::Value` conversion automatically. The SWC binding also uses this pattern (opts: any -> TransformOutput).

   The function is synchronous in Rust but platform.ts calls it as `binding.transform_modules(opts)` which returns `Promise<TransformOutput>`. Check platform.ts line 159: `transform_modules: (opts: any) => Promise<TransformOutput>`. Since the SWC native binding returns synchronously and the TS layer wraps it, the NAPI function should be synchronous (napi-rs will return it as a resolved value, and the TS async wrapper handles the rest).
