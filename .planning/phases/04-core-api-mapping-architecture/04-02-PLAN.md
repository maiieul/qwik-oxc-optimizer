**Section 3: Data Flow Specification (ARCH-03)**

Document the complete pipeline with type signatures at each transition:

```
TransformModulesOptions
  -> for each TransformModuleInput (parallel via rayon):
       -> parse(source, filename) -> Result<Program<'a>, Vec<Diagnostic>>
       -> SemanticBuilder::build(&program) -> Scoping
       -> collector::collect(&program, &scoping) -> CollectResult
       -> QwikTransform::new(options, collected).traverse(&mut program)
       -> code_move::extract_segments(&transform) -> Vec<SegmentProgram<'a>>
       -> emit::codegen(program, segments) -> Vec<TransformModule>
  -> aggregate: Vec<TransformModule>, Vec<Diagnostic>
  -> TransformOutput
```

For each stage, document:
1. Input types (exact Rust signatures)
2. Output types (exact Rust signatures)
3. Which module implements it
4. What state/side-effects it produces
5. Error handling: what can fail and how errors propagate

Include an internal type `CollectResult` showing what the collector produces:
- `dollar_imports: HashSet<String>` -- known $-suffixed imports from @qwik.dev/core
- `dollar_calls: Vec<DollarCallSite>` -- located $-call sites with span info
- `module_imports: Vec<ImportInfo>` -- all import declarations
- `module_exports: Vec<ExportInfo>` -- all export declarations

Include an internal type `DollarCallSite` showing what gets recorded per $-call.

**Section 4: Test Harness Design (ARCH-04)**

Document the complete test strategy:

1. **Spec file parser** -- How to parse the 162 markdown spec files to extract:
   - Test configuration (from the table at the top)
   - Input source code (from the `## Input > ### Source Code` code block)
   - Expected output modules (from `## Output > ### Module: {name}` code blocks)
   - Expected segment metadata (from `#### Segment Metadata` JSON blocks)
   - Expected diagnostics (from `## Diagnostics` JSON block)

2. **Test runner structure** using `#[cfg(test)]` and `insta`:
   - One test function per spec file, or a parameterized test over all specs
   - Each test: parse spec -> build TransformModulesOptions -> call transform_modules -> compare output
   - Comparison strategy: use `insta::assert_snapshot!` for code output, `assert_eq!` for segment metadata fields

3. **Progressive testing order** -- which spec files to target first (simplest to most complex):
   - Tier 1 (basic extraction): example_1, example_2, example_3
   - Tier 2 (component pattern): example_functional_component, example_functional_component_2
   - Tier 3 (captures): example_capture_imports, example_multi_capture
   - Tier 4 (inline strategy): example_inlined_entry_strategy
   - Tier 5 (JSX): example_jsx, example_jsx_keyed
   - Tier 6 (edge cases): everything else

4. **Spec file location** -- tests reference `.planning/spec/*.md` relative to workspace root. Document how `CARGO_MANIFEST_DIR` or a test fixture path should be configured.
