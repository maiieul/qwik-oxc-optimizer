Fix several related capture issues:

**Issue A: JSX event handler capture filtering too aggressive (lines ~1261-1285)**

The current capture filtering for JSX event handlers requires the captured variable to be in `all_parent_decls` (union of all capture_stack frames' body_local_decls) OR `module_level_decls`. But variables declared in the component$ body (e.g., `const children = ...`, `const state = useStore(...)`) ARE in the capture_stack's body_local_decls at that point. The issue is specifically for cases where:

1. The variable is declared in the component body
2. Used in a nested $() segment
3. The $() segment is NOT a direct child but nested further (e.g., inside a JSX tree)

Check if the filtering logic at line 1273 properly includes variables from ALL capture_stack frames. The `all_parent_decls` is built from `self.capture_stack.iter().flat_map(|(_, decls)| decls.iter().cloned()).collect()` which should include component body vars. If a variable is still missing, it means it wasn't added to `body_local_decls` during traversal.

Debug approach: For test `example_jsx` (missing `children` capture), trace whether `children` appears in any capture_stack frame's body_local_decls when the nested segment's captures are computed. The issue may be that the variable declaration traversal (`enter_variable_declarator`) doesn't push to capture_stack if we're at certain nesting depths.

For `should_extract_single_qrl_with_nested_components` (missing `item` capture): `item` is likely a parameter of a .map() callback arrow. The callback arrow params ARE added to capture_stack's local_decls, but only for the innermost scope. Check if map callback parameters are being properly tracked.

**Issue B: Outer loop variable capture (should_transform_nested_loops)**

`current_iteration_vars()` returns `iteration_var_stack.last()` (innermost loop only). For nested loop event handlers, outer loop vars like `row` should be CAPTURED (not injected as params). Currently, the iteration variable filtering at lines ~1299-1313 only filters innermost loop vars. But `analyze_lambda_captures` is called before iteration var filtering, so outer loop vars should appear in `body_ident_refs`.

The fix: When computing `used_iter_vars` (line 1201), only use `iteration_var_stack.last()` (innermost loop). Do NOT include outer loop variables. Outer loop variables should remain in `capture_names` after compute_captures.

However, there's a subtlety: the `iter_var_param_names` filtering at line 1299 only removes the vars that were added to param_names. Since only innermost loop vars are added to param_names (via `current_iteration_vars()` which returns `last()`), outer loop vars should already be preserved. Debug to confirm this is happening correctly for `should_transform_nested_loops`.

**Issue C: C03 diagnostics for invalid segment expressions (example_invalid_segment_expr1, example_exports)**

For `example_invalid_segment_expr1`: SWC emits C03 diagnostics for capturing `style` and `render` (which are import references in certain contexts). OXC captures them instead. Check if these identifiers should be classified differently -- possibly they're in `dollar_imports` or should be treated as framework imports.

For `example_exports`: Missing captures (obj, v1, v2, v3) plus C03 not emitted. These variables are likely module-level but the reclassification is converting them to self-imports rather than captures. Check if `reclassify_module_level_decl_captures` is incorrectly handling these.

**Issue D: Capture ordering (should_extract_single_qrl, should_extract_single_qrl_with_index, should_transform_qrls_in_ternary_expression)**

These tests have captureNames ordering differences. After all the above fixes, verify that capture_names are sorted alphabetically after ALL processing steps. If ordering differs, ensure the final sort happens AFTER all filtering (invalid_decl, iteration var, module-level reclassification).
