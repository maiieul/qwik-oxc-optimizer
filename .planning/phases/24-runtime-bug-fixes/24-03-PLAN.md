Fix capture analysis so segment capture variable lists match expected output. There are two distinct patterns:

**Pattern A: capture-diff (14 deviations)**
Both expected and actual use captures, but the variable lists differ. For example, spec `example_jsx` has segment `test.tsx_Foo_component_1_DvU6FitWglY.js` where the expected and actual capture lists disagree on which variables from the parent scope need to be captured.

Diagnose by comparing a specific failing spec's expected output (from the spec markdown) with actual output. Check:
1. The capture_stack tracking in transform.rs -- does it correctly push/pop frames on entering/exiting $-bodies?
2. The identifier reference recording in the capture_stack -- does it see ALL references in the body, including those in nested arrow functions, template literals, property accesses?
3. The local declaration tracking -- does it correctly exclude parameters, let/const/var declarations within the body, and function declarations?
4. compute_captures() in collector.rs -- does it correctly classify each reference as LocalCapture vs ImportReemit vs global?

Common issues to check:
- Props destructuring: if a component$ has `({ count, name })` and the onClick$ body uses `count`, is `count` seen as a capture (it should be since it's from the parent scope)?
- Function parameters: if an arrow function has `(ev) => { ... }`, `ev` should NOT be captured
- Shadowed variables: if the body declares `const x = 1` and also references an outer `x`, only the outer one should be captured
- Import references: symbols that are imports should be reemitted, NOT captured

**Pattern B: empty-segment-capture (13 deviations)**
Segments have empty bodies where capture code is expected. These are likely residual from Plan 01's QRL extraction fix. If some still remain after Plan 01, investigate why these specific segments have empty body_code despite having capture_names. The issue may be that:
- The segment exists (was created by create_jsx_event_segments_recursive)
- But the body code was never serialized (segment_body_codes has no entry for this span)

If empty-segment-capture persists, the fix is the same as Plan 01 -- ensuring body serialization happens for these specific lambda patterns.

**Pattern C: const-let-var differences (20 deviations)**
The actual output has different numbers of const/let/var declarations. This often indicates:
- Missing intermediate variables (e.g., capture restoration adds `const x = _captures[0]` that expected code doesn't have, or vice versa)
- Different destructuring patterns (e.g., `const { a, b } = props` vs separate `const a = props.a; const b = props.b`)
- Extra or missing variable declarations from code movement

Diagnose 2-3 representative specs (e.g., `example_2`, `example_4`, `example_5`). Compare the expected and actual code line by line. The const-let-var difference is often a symptom of other codegen issues (incorrect capture restoration, different props destructuring strategy, or different code serialization approach).

Fix the root causes. The fixes likely involve:
1. Correcting the capture_stack walk to match SWC's capture tracking behavior
2. Ensuring capture variable order matches the expected encounter order
3. Fixing props destructuring codegen to match expected patterns

After fixes, run `cargo test --package qwik-optimizer-oxc` to ensure no regressions.
